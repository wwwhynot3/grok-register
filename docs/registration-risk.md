# 注册链路与 x.ai 风控的对抗分析

> 面向想深挖的读者。行动版结论在 README 的 FAQ「注册流程会不会被封?」。
> 本文不保证时效:收紧是持续的,看完以 README 故障排查表为准。

## 1. 对抗模型:谁控制什么

```
我们控制:  浏览器形态(有头/指纹) · 出口 IP(节点轮换) · 注册时序 · TLS 指纹 · 打码器
x.ai 控制: 端点行为 · 是否静默 · 每日配额 · 新挑战类型 · 验证码是否真的送达
```

模仿的是"流程",判定权在对方手里。他们不需要证明你是机器人——只需要让某一环
**悄悄不产出**(接口 200 但邮件不发),模仿流程的产出就归零,而你的成本照付
(买邮箱、打码)。

## 2. 检测面(6 类)

| # | 检测面 | 机制 | 我们暴露的信号 |
|---|---|---|---|
| 1 | **静默拒绝** | 不改变接口,按 IP/UA/节奏降权:码延迟、随机丢弃 | 邮件 75s 超时;HTTP 全 200 |
| 2 | **行为指纹** | 真人注册有表单交互事件(focus/input/鼠标),我们绕 UI 直 POST | 服务端遥测看到"无交互提交" |
| 3 | **协议结构重放** | grok_free 的直 POST 依赖硬编码 Next.js `state_tree`——模拟点击后的内部状态机 | 前端一升级,POST 即 400 |
| 4 | **指纹检测** | TLS(JA3/JA4)、headless、CDP 自动化标记 | 旧指纹 403;headless 被拦 |
| 5 | **账号侧收紧** | 邮箱域名拉黑、要求手机验证、按 UA 集群/节点 IP 段降权 | 注册"成功"但码不来 |
| 6 | **配额硬顶** | 每日发码 ~20-25 个,24h 抑制窗口——**与 IP 无关,按账号池记账** | 轮换多少节点都没用 |

## 3. 历史收紧编年(仓库实历,均击穿过当时的"模仿")

| 时间 | 事件 | 现象 → 判断依据 | 应对 |
|---|---|---|---|
| 早于 2026-08 | TLS 指纹封杀 | 旧别名(chrome120/124/131)直接 403 | `GROK_IMPERSONATE` 换最新指纹 |
| 2026-08-06 | PKCE 路径被 CF 拦截 | 授权页无法处理 consent | 弃用 PKCE,统一 Device Flow |
| 2026-08-14~15 | headless 浏览器被拦 | 授权页 TITLE 空/重定向登录页 | 有头浏览器 + Xvfb |
| 2026-08-15 | gRPC 发码/验证静默封杀 | HTTP 200 但邮件不送达 | 弃 grok.py,重构 grok_free 表单流 |
| 2026-08-15 | gmail 变体 base 被拉黑 | 变体邮箱收不到码 | 换 ms_imap 买断 |
| 2026-08-15 | self_built 域名被明确拒绝 | 注册被拒 | 同上 |
| 2026-08-15 | 节点级硬拦截 | `Blocked due to abusive traffic patterns`(浏览器也过不了) | `GROK_SKIP_NODES` 黑名单 |
| 2026-08-15 | 单 IP 发码限流 | 同 IP 连注册 ~3-5 个后无码 | 每号轮换出口 IP |
| 2026-08-16 | 每日发码配额硬顶 | 全天累计 ~20-25 个后所有节点收不到码 | 零增长熔断 + 次日恢复 timer |
| 2026-08-16 | RT 批量吊销 | 83 账号 refresh 报 `invalid_grant` | `reauth_batch` 用 SSO 批量重铸 |

**共性模式**:每次收紧都是"分类打击"(堵一条路),且多半是**静默**的——发现靠
产出归零 + 日志特征,不是靠报错。这也是为什么项目把"止损"做成第一原则。

## 4. 未来收紧的预测框架(按可能性排序)

1. **静默降权**(最便宜,最可能):接口不变,按 IP 段/UA 集群/注册节奏延迟或丢弃码。
   判断:某节点/某 UA 下码率骤降但接口全 200。
2. **前端结构升级**:`state_tree` 等内部状态机变更 → 直 POST 400。
   判断:grok_free 突然整批 400,浏览器手工注册却正常。
3. **新验证维度**:注册要求手机号/二次验证;Turnstile 升级或叠加新挑战。
4. **账号侧**:更多邮箱域名拉黑;SSO 短期化(缩短 SSO 有效期)。
5. **配额继续下调**:从 ~20-25/日 压到个位数,或按账号池而非 IP 记账。

## 5. 应对优先级与止损原则

- **止损第一**:连续 N 轮零产出(`GROK_FREE_CIRCUIT_STREAK`)立即熔断到次日,
  **不要在死路上重试烧钱**(每次重试 = 新买邮箱 + 新打码)。
- **换路顺序**:引擎(grok_free → grok.py)→ 邮箱商(ms_imap → 其他)→ 指纹
  (`GROK_IMPERSONATE`)→ 节点(轮换组/黑名单)。
- **多路径是生存策略**:x.ai 每次堵一条,总有一条还通着;README 标注了
  "仅 LuckMail(ms_imap)实测跑通",其余提供商是备用路径,换之前先小批量验证。
- **静默收紧的识别**:盯 `status.py` 的注册成功率——成功率骤降但无报错 =
  大概率被静默降权,比"失败"更难发现,更需要看趋势。
